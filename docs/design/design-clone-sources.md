# SMART PLATFORM — Design Clone Sources

**Goal:** state which open-source projects this team may clone code from, which we may only read for design patterns, and which are off-limits — so that a team with no UX/UI designer can legally lift layout, information architecture, empty states, tables and motion from the best existing implementations without importing a licence obligation.

**Method:** every licence below was read from the repository's own `LICENSE` / `LICENSE.md` / `LICENSE.txt` file (raw file fetch) or from the GitHub repository API `license` object — **not** from listicles or recall. Stack claims were read from `package.json`. Where a claim comes from reasoning rather than source text it is labelled `[inference]`; where verification could not be completed it is labelled `[unverified]`.

**Scope:** the target is a Saudi-market multi-tenant ERP plus marketing site on Next.js 15 (Pages Router), React 18.3, TypeScript strict, Tailwind CSS **3.4.17**, daisyUI 4, i18next, Arabic-RTL-first. We clone **design** — layout, IA, empty states, tables, motion — never ship someone else's product.

**Companion:** `docs/design/design-system-adoption.md` decides which design systems and art direction we adopt; `docs/design/design-synthesis.md` decided the tokens. This document decides which repositories we are allowed to learn from and copy out of.

## 2. The one rule that matters

> **Copyright protects code and other fixed expression. It does not protect UI ideas, information architecture, layout concepts, empty-state strategy, or motion policy.**
> Reading a copyleft repository (even AGPL) to _learn_ its information architecture, screen inventory, empty states and motion, then re-implementing that in your own markup and your own CSS, is normal industry practice and is not, by itself, a derivative work.
> Copying class strings, CSS, component files, or generated markup out of that repository **is** creating a derivative work — and for AGPL/GPL that derivative inherits the copyleft.

**Operational rules for this repo**

- **Read-only tier (AGPL/GPL/LGPL/BUSL/ELv2):** screenshots + written specs only. The written spec must be prose/bullets describing _what the screen does and why_, not transcribed markup. No source file should be open in an editor during implementation.
- **Clean-room process (apply to every copyleft project, no exceptions):** (1) one person reads the source and writes a spec; (2) a different person implements from the spec; (3) the spec contains no code, class names, file paths or identifier names; (4) screenshots are of the _running app_, not of code.
- **Copyable tier:** only files whose licence is verified permissive (MIT/Apache-2.0/BSD-3-Clause) **and** not inside a carve-out directory (§10.8). Copying permissive code still requires retaining the copyright notice and licence text — MIT, Apache and BSD all require notice retention.
- **Attribution hygiene:** keep a `CLONE-SOURCES.md`-style table mapping any copied file → upstream repo → licence → notice. Apache-2.0 additionally requires stating changes and carries a patent grant; MIT requires the notice; BSD-3 forbids using the project's name to endorse.

> **Not legal advice.** This is engineering guidance written by a researcher, not counsel. The licence wall in §10 is derived from the files cited there; it is not a legal opinion on your specific use.

### 6.3 The five patterns worth lifting, described concretely

Every stack fact below is direct evidence from the `package.json` files cited in §6.1–6.2; the prescribed _implementation shape_ is `[inference]`.

1. **Journal / ledger grid with a sticky account column and a running-balance column.**
   - Shape: two-axis virtualised table; left column group (Date, Account code, Account name) pinned via `position: sticky` with an explicit `inset-inline-start` (logical property, so it flips automatically in RTL — do **not** use `left`); right group (Debit, Credit) right-aligned with tabular-nums; a `Balance` column that is a _derived running sum computed over the whole filtered result set_, not the visible page — otherwise the running balance is wrong the moment you paginate or virtualise.
   - Evidence for the grid stack: `react-table-sticky` in Bigcapital; `@tanstack/react-table` + `@tanstack/react-virtual` in Medusa; `mantine-datatable` in InvenTree.
   - RTL trap: pinning must be inherited from the filter/sort model. A ledger that is _sorted_ by account but _displayed_ in Arabic must keep the account column first in both directions — logical properties give you this for free.
2. **Report filter bar with saved presets.**
   - Shape: a single horizontal bar above the report: period control (This month / Last month / This quarter / custom range), entity selector (company/branch), then a `Presets` dropdown holding named filters ("VAT return – Q3", "Unposted JEs"), with the active preset shown as a removable chip. Filters serialise to the URL so a report is shareable and the back button works.
   - Evidence: Medusa's URL-persisted table filters via TanStack Table; Frappe UI's `Filter`/`List` primitives. The "save as preset" UX itself is a Frappe-ERPNext / dub-style pattern — `[inference]`.
3. **Global multi-entity company switcher.**
   - Shape: a persistent switcher in the top bar showing _entity name + tax registration number_ (not just a name — in KSA the VAT number disambiguates the branch), grouped by legal entity → branch, with keyboard search. Switching must remount the whole data layer (query cache keys include `companyId`) and must be reflected in the URL/tenant header, since a company switch changes the chart of accounts, the tax rules and the ZATCA business settings for that branch.
   - Evidence: Frappe/ERPNext multi-company is native to the data model (KSA Compliance declares "Multi-company support" as a headline feature — <https://github.com/lavaloon-eg/ksa_compliance/blob/master/README.md>). dub's and twenty's workspace switchers are the cleanest React implementations to study (both read-only tiers).
4. **Invoice editor / preview split pane.**
   - Shape: resizable two-pane with the form on one side and the rendered tax invoice on the other, updating live; the preview must render in the _document's_ direction (`dir="rtl"` for Arabic, independently of the UI language). Persist the split ratio per user.
   - Evidence: `react-resizable-panels` ships in both the Novu dashboard and Supabase Studio; Supabase Studio also uses it alongside `react-grid-layout`.
5. **Transaction-to-document match-review row with a confidence badge.**
   - Shape: a review list where each row is _bank/receipt line_ → candidate _document_ (invoice, payment entry) with: amount delta rendered as a signed, colour-coded number; date delta in days; a **confidence badge** (High / Medium / Low) with the _reason_ in a tooltip ("exact amount + exact date", "amount match, ±5 days", "name similarity"); and three actions in a fixed cell: Match, Split, Create new. Keyboard: `J/K` to move, `Enter` to accept, `X` to reject. The badge is the whole point — it turns an O(n²) reconciliation into a triage queue.
   - Evidence: Bigcapital is the accounting app with `react-table` / `react-table-sticky` and RTL plumbing; the badge/triage UX itself is `[inference]`.

### 7.2 Its Phase-1 print format, in detail

Source: <https://raw.githubusercontent.com/lavaloon-eg/ksa_compliance/master/ksa_compliance/ksa_compliance/print_format/zatca_phase_1_print_format/zatca_phase_1_print_format.json> (`"print_format_type": "Jinja"`, `"doc_type": "Sales Invoice"`, `"font_size": 14`, margins 15pt, `"page_number": "Hide"`).

- **`"default_print_language": "ar"`** — Arabic is the default print language.
- **Direction is set per-render from the language name, not the locale code:** `{% if lang == "العربية" or lang == "اردو" or lang == "پارسی" %}{% set dir = "rtl" %}{% else %}{% set dir = "ltr" %}{% endif %}` — Arabic, Urdu and Persian get `dir="rtl"`. `dir` is then applied to each of the three data tables (`<table … dir={{ dir }}>`). _Design takeaway:_ RTL here is per-document, not per-UI — the printed artefact's direction is driven by the print language.
- **Heading switches on transaction type and document kind.** `type_of_transaction` ∈ {`Standard Tax Invoice`, `Simplified Tax Invoice`, `Both`}; when `Both`, it picks **Standard if the buyer has a VAT number, else Simplified**. Heading text resolves to one of six: Standard Tax Invoice / Standard Tax Invoice Credit Note / Standard Tax Invoice Debit Note / Simplified Tax Invoice / Simplified Tax Invoice Credit Note / Simplified Tax Invoice Debit Note (driven by `doc.is_return` and `doc.is_debit_note`).
- **Header row:** Invoice ID (`doc.name`) and Posting Date, in a 6/6 column split.
- **Seller table** (3 columns, `dir` applied): **Seller Name** | **Address** | **VAT Registration Number**. Address is composed as `street, district, city | postal_code`.
- **Conditional buyer table:** rendered **only when `invoice_type == "Standard" and customer_vat_reg_no`**, with **4 columns**: Buyer Name | Address | VAT Registration Number | **Commercial Registration Number**. The CR number is fetched as `frappe.db.get_value("Additional Buyer IDs", {"parent": doc.customer, 'type_name': 'Commercial Registration Number'}, 'value')`.
- **Blocking error for a Standard invoice whose buyer has no VAT number:** an impossible-to-miss red state — a msgprint `<div style="display:none">` with `title='Error', msg="Customer does not have VAT registraion Number", indicator="red"` plus a visible `<p class="h2 text-danger">{{ doc.customer }} : Customer does not have VAT registraion Number</p>`. _(The typo "registraion" is in the source.)_ **This is the single most important behaviour to replicate:** a Standard tax invoice is not merely warned about — it is blocked and the buyer name is echoed back.
- **Also blocking:** if there is no active Phase-1 business settings row, the same pattern prints `"Does not have active ZATCA Phase 1 Business Settings"` with the company name in red.
- **Items table — columns and fixed widths, exactly:** `#` = 3% | Products = 20% | Unit Price = 15% | Quantity = 10% | VAT % = 10% | VAT Amount = 15%. Product cell shows `item_name` and, if it differs, `Item Code: …` on a second line underneath. Numeric cells use `text-align: right` and `frappe.utils.fmt_money(...)`; quantities/tax are rendered with `| abs`.
- **Totals block** (its own 2-column bordered table): row 1 = **VAT Amount** (`total_taxes_and_charges`), row 2 = **Total With VAT** (`grand_total`).
- **QR:** `<img src="data:image/png;base64, {{ get_zatca_phase_1_qr_for_invoice(doc.name) }}" width=200 height=200>` inside a `text-center` wrapper — **centred, 200×200, base64 PNG**.
- Optional `letter_head` block is emitted at the top when present.

### 7.4 `wes4m/zatca-xml-js` — MIT, TypeScript — the ONE ZATCA artefact you may vendor

- **Licence (read directly):** "MIT License, Copyright (c) 2022 Wesam Alzahir" — <https://raw.githubusercontent.com/wes4m/zatca-xml-js/main/LICENSE> ; the GitHub API confirms `"license": {"spdx_id": "MIT"}` — <https://api.github.com/repos/wes4m/zatca-xml-js>
- **What it does:** EGS (E-Invoice Generation System) creation/on-boarding with **Compliance and Production x.509 CSIDs** and cryptographic stamps; **Simplified Tax Invoice** creation, signing, compliance checking and reporting. Documented flow: `egs.generateNewKeysAndCSR(false, "solution_name")` → `egs.issueComplianceCertificate(otp)` → `egs.signInvoice(invoice)` → `egs.checkInvoiceCompliance(...)` → `egs.issueProductionCertificate(compliance_rid)` → `egs.reportInvoice(...)`. Implements UBL 2.1, ISO EN16931, UN/CEFACT code lists 1001 and 5305, ISO 3166, ISO 4217:2015, plus the security stack (NCA NCS-1:2020, ETSI EN 319 102-1/132-1/142-1/122-1, W3C XML-Signature, RFC 5280/5035/5652, ISO 32000-1). Source: <https://raw.githubusercontent.com/wes4m/zatca-xml-js/main/README.md>
- **Exact caveats:**
  - The README banner reads **`v0.1.9 (experimental)`**.
  - **Last code change ~March 2024:** GitHub `pushed_at` = `2024-03-08T02:02:46Z` (the repo `updated_at` 2026-08-09 reflects stars, not code) — <https://api.github.com/repos/wes4m/zatca-xml-js>
  - **The npm package is older than the last commit.** npm `latest` (0.1.9) was published **2022-12-09** — `"0.1.9":"2022-12-09T13:06:09.261Z"`, registry `modified` 2022-12-09 — <https://registry.npmjs.org/zatca-xml-js>. **Pin from git, not npm**, if you need the 2024 state.
  - **It explicitly does NOT do standard tax invoices:** _"I'm not planning on supporting `Tax Invoices` (Not simplified ones)."_ If your ERP must issue B2B Standard invoices, this library covers only half of your compliance surface.
  - **The `EGS` module requires OpenSSL on the host:** _"The `EGS` module in the package is dependent on OpenSSL being installed in the system it's running on. It's being used to generate an `ECDSA` key pair using the `secp256k1` curve. also to generate and sign a CSR."_ Everything else works without it.
  - The roadmap admits CSID renewal/revocation is missing, and XML templates are populated with string `replace` rather than a template engine.
- **Verdict:** safe to vendor for simplified-invoice signing/reporting and for EGS onboarding; **do not treat it as a complete ZATCA compliance layer.**

### 9.2 What to steal from each token architecture

- **Primer Primitives — the best token pipeline to copy.** Layered tokens (base primitives → functional/semantic tokens) with **per-theme override files**, compiled by **Style Dictionary** down to plain CSS custom properties. The value for us: one source of truth generates our CSS vars, our Tailwind theme (v3 `theme.extend`) _and_ our daisyUI theme (`daisyui` config consumes CSS vars), so a rebrand touches one JSON file. Reference: <https://primer.style/foundations/primitives/getting-started> — the token-architecture description is `[inference]` from the pipeline's published structure; the licence is direct evidence.
- **Material Design 3 tokens — Apache-2.0 reference-to-system aliasing plus a formal RTL spec.** M3 documents _reference tokens_ → _system tokens_ aliasing (<https://m3.material.io/foundations/design-tokens>) and ships the **bidirectionality & RTL foundation page** (<https://m3.material.io/foundations/layout/bidirectionality-rtl>), the only _formal, standards-grade_ RTL layout spec in the mainstream design systems. Read that page before writing any Arabic layout rule.
- **Radix Colors — the 12-step scale with fixed step semantics.** "Each step in Radix Colors scales is designed for a specific use case"; steps 11 and 12 are the text steps and "are guaranteed to Lc 60 and Lc 90 APCA contrast" — <https://www.radix-ui.com/colors/docs/palette-composition/understanding-the-scale> , with aliasing guidance at <https://www.radix-ui.com/colors/docs/overview/aliasing>. **Why it matters:** it gives a defensible answer to "which of these 12 shades do I use for a table row border" without a designer, and it is MIT so we can literally ship the scale.
- **Ant Design — seed/map/alias tiering plus a direction provider.** Docs: "Seed Token … Map Token … Alias Token" with `ConfigProvider theme={{token:…}}` — <https://ant.design/docs/react/customize-theme/> ; the source comment in `components/theme/util/alias.ts` reads _"Seed (designer) > Derivative (designer) > Alias (developer)"_ — <https://github.com/ant-design/ant-design/blob/master/components/theme/util/alias.ts>. **Direction API:** `<ConfigProvider direction="rtl">` with `direction` = `ltr | rtl` — <https://ant.design/components/config-provider/> , <https://github.com/ant-design/ant-design/blob/master/components/config-provider/index.en-US.md>. That three-tier naming and a top-level `direction` prop is exactly our model.
- **Carbon — spacing scale and 2x grid; RTL is unfinished, so do not copy its RTL story.** Carbon is Apache-2.0. Its 2x grid and spacing scale are the cleanest published numeric systems (<https://carbondesignsystem.com/elements/2x-grid/overview> , <https://carbondesignsystem.com/elements/spacing/overview>). **But note:** RTL has been an open, component-by-component effort — the umbrella issue `BIDI - Support base text direction` #7264 carried labels including `type: bidi ↔️` and **`planning: umbrella`**, created 2020-11-10 and closed only 2023-10-30 (<https://github.com/carbon-design-system/carbon/issues/7264>), and the migration to CSS logical properties for RTL landed later still, with a follow-up "fix outstanding issues in RTL mode" issue #14544 (<https://github.com/carbon-design-system/carbon/issues/14544> , <https://github.com/carbon-design-system/carbon/issues/13619> , <https://github.com/carbon-design-system/carbon/pull/14531>). **Lesson for us: use CSS logical properties from day one so RTL never becomes a backlog.** That is a design decision we can make for free and Carbon could not.

### 9.3 Documentation-site structures worth imitating

- **GOV.UK per-component page contract:** each component page follows _When to use this [component/pattern]_ → _When not to use_ → _How it works_ → _variants_ → _accessibility_ → _research_. The template file states: "All design patterns and components in the GOV.UK Design System should follow the below content pattern. … ## When to use this [component/pattern] … If necessary, include an additional H2 titled 'When not to use…'". Sources: <https://github.com/alphagov/govuk-design-system-backlog/blob/main/docs/DESIGN_SYSTEM_CONTENT_PATTERN.md> ; live examples <https://design-system.service.gov.uk/components/text-input/> , <https://design-system.service.gov.uk/components/breadcrumbs/> , <https://design-system.service.gov.uk/components/details/> , <https://design-system.service.gov.uk/components/tabs/> . **Adopt this verbatim for our internal component docs** — it is the highest-leverage artefact we can produce without a designer, because "when _not_ to use" is how a design system actually prevents drift.
- **Carbon's top-level IA** — Elements / Components / Patterns / Guidelines plus a separate _Data visualization_ axis — <https://carbondesignsystem.com/> (structure is `[interpretation]` from the live site; licence verified separately).
- **Polaris token pages** — per-token-family pages with a _do/don't_ example and a copyable token name. Two blockers: **the repo is archived/deprecated** and **the licence is restricted** (§9.1). Read the _page structure_; take nothing else. <https://polaris.shopify.com/tokens/color>

### 9.4 The de-genericising recipe

`[inference]` — a prescription based on the token systems above, not a quotation from any source.

1. **Never use a framework default for a decision we can name.** daisyUI's default theme, Tailwind's `gray`/`slate`, shadcn's `zinc` — replace each with a token whose name states its job (`--surface-raised`, `--border-subtle`, `--text-muted`).
2. **Three tiers only:** primitives (raw values) → semantic (role names) → component (e.g. `--table-row-hover`). This is the Primer/AntD shape (§9.2).
3. **Two rules that kill "AI-looking" UI:** (a) one accent hue only, taken from Radix and used at _one_ of its 12 steps for solid fills (step 9) — never a gradient; (b) a single spacing scale (4/8-based) with zero arbitrary values, so every gap is defensible.
4. **Arabic-first typography from the start:** a proper Arabic face with the weight range you actually use, explicit `line-height` (Arabic needs more), and `letter-spacing: 0` (never apply Latin tracking to Arabic). _This is the single most visible differentiator and no template gives it to you._
5. **Motion policy, not motion sprinkles:** define 3 durations and 2 easings as tokens; every transition references a token; respect `prefers-reduced-motion`. Steal the _discipline_ from Huly's list density and cal.diy's booking flow.

### 9.5 Defaults that are the most AI-reproduced (avoid)

`[inference]`, offered as a heuristic rather than a measured fact:

- **Ant Design defaults** — immediately recognisable blue `#1677ff` plus 6px radius.
- **Material 3 defaults** — the dynamic-purple seed and the 28px "pill" radius.
- **shadcn/ui defaults** — `zinc`/`slate` neutrals, `rounded-lg`, `border` at 1px with no shadow.
- **Untitled UI greys** — the very neutral, high-density grey ramp that reads as "generic SaaS dashboard".

If two of those four appear side by side in a screenshot, the product reads as unreviewed. Any of the four is _fine_ as a starting point; none should ship unmodified.

## 12. Unresolved, unverified and contradictory

Kept separate from the decisions above so nobody mistakes a guess for a fact.

### 12.1 Contradictions

1. **cal.com's licence is disputed across time and across sources.** The live repo is MIT (`calcom/cal.diy`); a large body of search results and GitHub issues still assert AGPLv3 + EE, and older commits genuinely are AGPLv3 + Commercial. Any document that says "cal.com is AGPL-3.0" is describing the pre-April-2026 repository. Both statements are true of different refs — **use the date-stamped form.** <https://raw.githubusercontent.com/calcom/cal.diy/main/LICENSE> vs <https://github.com/calcom/cal.com/blob/11bddbb71dc4db7f53c4e3bbdb28d67dac6ee54e/LICENSE> and <https://github.com/calcom/cal.com/issues/15370>
2. **`zatca-xml-js` "last updated" depends on which registry you read.** GitHub `pushed_at` = 2024-03-08; npm `latest` (0.1.9) published 2022-12-09. Unresolved; both are reported rather than picking one.
3. **Novu's licence is reported as AGPL in several secondary sources; the root LICENSE file is MIT.** Trust the file. There is nonetheless an `enterprise/` tree whose terms were not opened — treat it as restricted.
4. **Directus is widely described as BUSL-1.1; its current `license` file is MSCL-1.0-GPL.** GitHub's own API still says `NOASSERTION`, which is why secondary sources diverge.
5. **Carbon and RTL:** Carbon is often cited as RTL-ready, but its own tracker shows RTL was an umbrella effort spanning 2020→2023 with logical-properties regressions afterwards. The _marketing_ and the _issue tracker_ disagree; the tracker is the evidence.
