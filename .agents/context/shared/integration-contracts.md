# Integration contracts

Purpose: the real cross-repo contracts between ClientApp (Angular SPA), Inventory (WebAPI), and the smart-platform admin surface. Verified against the code on 2026-08-24; the `PlatformBilling` M2M block was re-verified against the ERP controller on 2026-09-13, and its response-shape traps against the ERP C# on 2026-09-14.

## Key points

- **SPA → WebAPI (HTTP)** — authenticated requests (cached JWT in `localStorage.authToken`) carry `Authorization: Bearer <token>` plus an `h-n: <hostname>` tenant hint; unauthenticated calls (login/register — no cached token) go out without either header, so auth endpoints never receive the tenant hint. Central caller `api-caller.service.ts` (30s default timeout), header injection in `http-interceptor.service.ts`. Base per `environment.active_server`: dev `http://localhost:5001/api/`, prod e.g. `https://server-erp.smartapro.com/api/`.
- **SPA → WebAPI (realtime)** — two channels: a SignalR hub `/notificationHub` (mapped in `Program.cs`) and a raw WebSocket endpoint `/ws` (`WebSocketMiddleware`). Two SPA consumers: `SignalRService` (currently hardcoded hub URL `https://localhost:44360/notificationHub`) and a raw `NotificationService` using env `wsUrl` (dev `ws://localhost:5001/ws`).
- **Platform → WebAPI (M2M)** — `X-Platform-ApiKey` header must equal `appsettings Platform:ApiKey`, compared with `CryptographicOperations.FixedTimeEquals` (`WebAPI/Attributes/PlatformApiKeyAttribute.cs`). **Verified 2026-09-02: key is set and identical on both sides** — `ERP_PLATFORM_API_KEY` (smart-platform `.env`) === `Platform:ApiKey` (ERP `appsettings.json`), 64-char hex. Mismatch returns 401; a missing header also returns 401 (`PlatformApiKeyFilter` yields `UnauthorizedResult` on an empty/mismatched header) — 500 only when the server-side `Platform:ApiKey` is itself unconfigured. Platform controllers: `TenantRegistration`, `SuperAdmin`, `PlatformBilling`, `TenantStatus` (+ `SuperAdminService` / `TenantRegistrationService`).
  - **`PlatformBillingController` — `api/platform/billing`, class-level `[PlatformApiKey]`** (verified against the C# on 2026-09-13): `GET subscriptions` · `GET subscriptions/by-tenant/{tenantId:guid}` · `POST subscriptions/by-tenant/{tenantId:guid}` (create — body `packageId`, `startDate`, `endDate`, `trialDays?`, `isTrial?`) · `POST .../extend` (body `newEndDate`) · `POST .../cancel` · `POST .../trial-override` (body `newTrialEndDate`) · `POST .../change-plan` (body `packageId`, `previewOnly`) · `GET system-modules` · `GET packages` · `GET packages/{id:guid}` · `PUT packages/{id:guid}/modules` (body `systemModuleIds`, `syncExistingSubscriptions`) · `POST subscriptions/sync-modules`. The kit wrappers (`lib/erp.ts`) and the platform-side contract notes live in `docs/platform-erp-api-contract.md`.
  - **Branch availability — read this before assuming an endpoint is callable.** These endpoints are merged into the ERP repo's **`development`** branch (PR #6); they are **not** in its `main`, and `PlatformBillingController.cs` itself does not exist on ERP `main` at all. A platform build pointed at an ERP `main` deployment will therefore 404 on every `/platform/billing/**` call. "ERP-side landed" means `development`, not "shipped to production".
  - **Two silent response-shape traps (verified against the ERP C# on 2026-09-14).** Both are invisible until you look at the bytes, and both bite anyone writing a normalizer or an audit snapshot:
    - **Status enums serialize as NUMBERS, not strings.** `GetSubscriptionByTenant` bypasses AutoMapper: `FindActiveSubscriptionAsync` returns the raw domain entity (`Task<Subscription?>` over `Domains/Entities/Platform/Subscription.cs`), and `Program.cs`'s `AddJsonOptions` registers **no** `JsonStringEnumConverter` (only the two DateOnly converters) — so `SubscriptionStatus { Trial=0, Active=1, Expired=2, Suspended=3, Cancelled=4 }` is emitted as `0`/`1`/…. A `SubscriptionResponseDto` _does_ declare `Status` as a `string` with a matching `CreateMap`, but that mapping serves only `GetAllSubscriptionsAsync` (`GET /platform/billing/subscriptions`) — **not** the by-tenant path. Platform consequences: `sanitizeSubscriptionSnapshot` keeps only `typeof status === 'string'`, so against a real ERP every audit before/after snapshot silently loses `status`; and the `cancel` route's `CANCELLABLE_STATUSES` pre-check (comparing `'active'`/`'trial'`) can never match, so a deliberate 409 degrades into an ERP round-trip. Scrutinise any new ERP field for the same class.
    - **POST endpoints return an action ack, not the subscription.** All four (`create`, `extend`, `cancel`, `trial-override`) return `PlatformActionResponseDto { Message, NewEndDate }` (`SuperAdminService.cs`) — camelCased to `{ message, newEndDate }`, no subscription fields, and `newEndDate` absent on cancel. Never build an audit `after` snapshot from a POST response; re-read `by-tenant`.
    - **Wrapper shape:** `GET by-tenant` answers `Ok(new { subscription })` → `{ "subscription": { … } }` (inner value `null` when the tenant has no Active/Trial row), not the bare entity. `sanitizeSubscriptionSnapshot` already tolerates both shapes via `raw.subscription || raw`.
  - **Plan Changes — `POST /api/platform/billing/subscriptions/by-tenant/{tenantId}/change-plan`** — a sub-contract of the M2M key point above; changes the tenant’s package and re-syncs its enabled modules.
    - **Status (2026-09-13)**: contract **spec** agreed kit-side (P3.2, contract-first) and now **implemented ERP-side** — `PlatformBillingController.ChangePlan` is live on ERP `development` (PR #6) with the request/response shapes below; kit wrapper is `changeTenantPlan` (`lib/erp.ts`). The earlier note that `development` exposed only get/extend/cancel is obsolete. Reminder: not present on ERP `main` (see the branch-availability bullet above).
    - **Auth**: `X-Platform-ApiKey` header required (`[PlatformApiKey]`). Missing or invalid API key returns `401 Unauthorized`.
    - **Request Body**: `{ "packageId": "<guid>", "previewOnly": boolean }` (default `previewOnly: false`).
    - **Response 200** (`applied=false` for `previewOnly=true`, `true` for apply; mirrors `ErpChangePlanResponse` in `lib/erp.ts`): `{ "subscriptionId": string, "tenantId": string, "oldPackageId"?: string|null, "oldPackageName"?: string|null, "targetPackageId": string, "targetPackageName": string, "oldPriceMonthly": number, "newPriceMonthly": number, "priceDifference": number, "requiresPayment": boolean, "applied": boolean, "status": string, "endDate"?: string|null, "enabledModules": [{ "id": string, "code": string, "name": string }], "enabledModuleCodes": string[], "message": string }` — always present: `subscriptionId`, `tenantId`, `targetPackageId`, `targetPackageName`, `oldPriceMonthly`, `newPriceMonthly`, `priceDifference`, `requiresPayment`, `applied`, `status`, `enabledModules`, `enabledModuleCodes`, `message`; omittable **and** nullable (`?`): `oldPackageId`, `oldPackageName`, `endDate` — the key may be absent entirely, or present with value `null`, so consumers must handle both `undefined` and `null`.
    - **Errors**: `400` for a same-package target (see **Same Package**) and for `[ApiController]` ModelState validation failures; `404` `{"error": "No active subscription for tenant."}` when the tenant has no Active/Trial subscription (expected to match extend/cancel). Kit callers branch on `ErpApiError.status`, never on message text.
    - **Payment Responsibility**: The ERP change-plan endpoint does not process or validate payment directly. `previewOnly=true` is used to calculate the required payment before checkout. For upgrades requiring payment, the Platform must call `previewOnly=false` only after successful payment confirmation. The ERP endpoint trusts the authenticated M2M Platform caller for this post-payment apply step. Payment lifecycle integration remains owned by P2.11/P2.14. _(Intentionally supersedes the P3.2 item-4 wording that had change-plan called before the price-diff payment; preview → pay → apply is the agreed flow.)_
    - **Downgrade Policy**: Downgrades take effect immediately upon apply (`previewOnly=false`). Modules not present in the new lower package are removed immediately. Downgrades do not generate refunds or credits (`priceDifference = 0`, `requiresPayment = false`).
    - **Same Package**: Requesting the currently active package returns `400 Bad Request` ("Target package is already the current subscription package.").
    - **Module Synchronization & Scope**: Subscription modules in `SubscriptionModules` represent active module entitlements derived from the subscription's package. On apply, old modules are purged and new package modules are attached atomically with `PurchasedPrice`. If a package has no modules, subscription modules become empty.
    - **Trial → Active Lifecycle**: The `change-plan` endpoint intentionally preserves current subscription status (`Active` or `Trial`). Trial-to-Active transition upon initial paid conversion remains owned by P2.14 and was not modified.
    - **End-to-End Payment Gateway Verification**: Real sandbox payment gateway processing and webhook orchestration belong to P2.11 / P2.14. The ERP change-plan endpoint fulfills the backend contractual guarantee and calculation logic.
    - **Database Atomicity**: Updating `subscription.PackageId`, removing superseded `SubscriptionModules`, and inserting new package `SubscriptionModules` are wrapped in an explicit atomic database transaction (`BeginTransactionAsync` / `CommitAsync` / `RollbackAsync`).
- **Tenancy (`TenantMiddleware`)** — tenant resolved from subdomain (`MultiTenancy:BaseDomain = smartapro.com`, e.g. `company.smartapro.com`) or the JWT `TenantId` claim; `h-n` passes the original host for cross-domain calls. JWT tenant **must** match the subdomain tenant (403 "Token does not belong to this tenant."). True super admin (`IsSuperAdmin=true`, no `TenantId`) bypasses; reserved subdomains `core/admin/api/www/platform`; subdomain-less unauthenticated requests pass (login/register/Swagger).
- **Payments verify (kit ← WebAPI)** — `GET /api/payments/verify/{reference}` returns `{ success: boolean, status?: "Pending" | "Paid" | "Failed" }`. `status` is **additive during rollout**: ERPs that predate P2.14 omit it and the kit falls back to the optimistic settle (see `shared/payments.md`). Kit reads it through the BFF `pages/api/public/erp/verify.ts` (`{ data: result }`, rate-limited 60/min) and the BFF now **validates the body** first (`erpVerifyResponseSchema`, PG-30): the envelope must be an object, and `success`/`status` must be boolean/string **when present**. Both fields stay optional so `{}` and `{ success: true }` — the pre-rollout shapes the optimistic settle depends on — remain legal; a non-object body, or a wrong-typed field, is answered `502 erp-malformed-response` instead of being passed on as a silently-empty success. An **unrecognised** `status` string is passed through verbatim, never coerced and never rejected (rejecting it would 5xx and the poller reads 5xx as transient). The response body is a contract fixture in `tests/fixtures/erp-contract.ts`, asserted by `__tests__/api/public-erp-contract.spec.ts`.
- **Payment contract fixtures + the ERP stub (PG-55, 2026-09-14)** — `tests/fixtures/erp-gateways.json` is the **single source of truth** for per-gateway ERP payloads (methods catalogue, per-gateway `POST /payments` results, and the `verify` outcomes keyed by reference **prefix**). It is read by BOTH `tests/e2e/support/erp-stub.cjs` and `__tests__/contract/erp-gateway-contract.spec.ts`, so the stub and the contract assertions cannot drift. `erp-stub.cjs` now also serves the three **public** payments routes (`GET /api/payments/methods`, `GET /api/payments/verify/{ref}`, `POST /api/payments`) alongside its existing platform-billing surface, which is what lets `tests/e2e/funnel/payment-contract.spec.ts` drive browser → BFF → stub with **no** `page.route` interception. The fixture's `methods._expected` block records the derivation the real schema + availability filter must produce, and the contract spec asserts the real code still produces it. **Scope:** these fixtures are hand-written from the documented contract, NOT captured from a live ERP — a green stub run is not live-gateway verification, which is blocked on the ERP half (PG-10/PG-11/PG-12).
- **Payments methods + packages (kit ← WebAPI)** — `GET /api/payments/methods?country=SA` returns `{ key, label, provider, available, iconUrl? }` entries and `GET /platform/TenantRegistration/catalog/packages` a list of packages. Both are validated per entry by the kit (`erpPaymentMethodSchema` / `erpPackageSchema`, PG-20) before the public BFF re-exports them: an entry that fails the contract is dropped, and `available: false` (or a **missing** `available`) methods are filtered out entirely, so the funnel only ever offers a gateway the ERP vouches for. A whole body that is not an array is `502 erp-malformed-response` rather than a partially-parsed pass-through.
- **Configuration & ports** — `FrontBaseUrl = https://erp.smartapro.com` (callbacks/payment redirect), `CorsDomains = http://localhost:4200` (ClientApp dev). Ports: ClientApp **4200** · WebAPI **5001** (http) / **7035** (https) · smart-platform dev **4002**. Subdomain-less tenants additionally gate on an active/trial subscription (403 "Subscription expired or inactive."; auth endpoints still allowed).
