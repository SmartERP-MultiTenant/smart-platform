# Payments across the product

Purpose: a map of how payments work across the three repos (WebAPI providers + standalone integrations + SPA-side payment UI). Not an implementation doc — see the code and `SmartAndPro.ERP.Inventory/docs/payment-system.md` for details.

## Key points

- **Method → provider (WebAPI `PaymentService`)** — current mapping: `card`/`mada`/`apple_pay` → **MoyasarProvider** (`PaymentService.cs`), `tabby` → **TabbyProvider** (mock), `tamara` → **TamaraProvider** (mock), `stc_pay` → **HyperPayProvider** (mock). **PaymobProvider** remains an available real provider (3-step token→order→payment-key) but is NOT the current selection for those methods. Map persisted in the `Payments` table; endpoint `POST /api/payments`, methods `GET /api/payments/methods?country=SA`.
- **Paymob (real)** — SPA drives the flow: `services/paymob` (`environment.paymob`: currency `EGP`, `integrationId` 5410149, `accept.paymob.com`) with `payment-callback.component` for the SPA-side return; WebAPI `PaymobProvider` handles the server side (`PaymobService` in Application layer).
- **Moyasar (current card/mada/apple_pay provider)** — `Providers/MoyasarProvider.cs`, registered in `Program.cs`/`PaymentService`, configured under `PaymentProviders:Moyasar` (a live-looking `sk_test_...` key is committed). Payer surface uses hosted redirect (Option A) rather than an embedded SDK — see decision [`docs/decisions/pg16-hosted-redirect.md`](../../docs/decisions/pg16-hosted-redirect.md). Not yet covered by `docs/payment-system.md` — treat the map above as current truth.
- **Standalone commerce/health integrations (not `PaymentService`)** — Salla and Zid (OAuth e-commerce, webhooks redirect to `erp.smartapro.com`), Wasafaty + CCHI (both NPHIES FHIR R4), ChannelManager (background sync service). Config under Salla/Zid/Wasafaty/CCHI/ChannelManager in `appsettings.json`.
- **Kit payment-result flow (`pages/payment/success.tsx`)** — after a gateway redirect the page polls the BFF `GET /api/public/erp/verify?reference=…` up to 15×2s (`attempts`/`interval` query knobs are localhost-only for e2e). Terminal states: `Failed` (or `success:false`) → `/payment/failed`; `Paid` → confirmed success copy + POST ERP handoff; explicit `Pending` at poll end → pending panel with **no** ERP CTA (the webhook activates the subscription); no `status` in the response (absent or blank) → **optimistic settle** kept for pre-P2.14 ERPs, which becomes unreachable once the ERP always returns `status`. A `status` that is present but **unrecognised** (e.g. `Succeeded`, a mistyped enum) polls to the pending panel and never claims success or hands over the ERP token. Non-2xx `verify` responses are split explicitly: a **4xx other than 429** is a permanent client-side rejection (unknown/oversized reference) and is a hard error that ends on the error panel, while a **429 or any 5xx** is a transient infrastructure failure whose body is never parsed — it falls through to the normal poll path, so an ERP/BFF outage during the poll window still settles optimistically rather than dead-ending a customer who already paid.
- **Public funnel BFF response contract (PG-20/PG-30/PG-52/PG-54, 2026-09-14)** — the four anon routes under `pages/api/public/erp/` (`methods`, `packages`, `verify`, `payments`) validate the ERP body and answer failures with a **stable code**, never upstream text. Three invariants to preserve when editing them:
  - **Contracts live in `lib/zod/erp.ts`** (`erpPaymentMethodSchema`, `erpPackageSchema`, `erpVerifyResponseSchema`, `readErpList`) and are applied in `lib/erp.ts` (`fetchAvailableMethods`, `fetchPackages`, `fetchVerifyResult`), not in the routes — so `/pricing`, which calls `getPackages()` straight from `getServerSideProps`, is covered by the same guard. Envelope strictness is all-or-nothing (a non-array list or a non-object verify body throws `ErpApiError('ERP_MALFORMED_RESPONSE', 502)`); **entry** strictness is per-item (a bad entry is dropped, one bad row never takes the catalogue down).
  - **Fail-closed on availability.** `erp.getMethods()` returns only entries the ERP marked `available: true`; an entry with a missing or non-boolean `available` is discarded rather than offered. A malformed `priceMonthly` **rejects its package** (absence of a price already renders as "Free" in `pages/pricing.tsx`, so a corrupt price could only become a false claim), while `description`/`priceYearly`/`trialDays`/`isActive` are merely dropped.
  - **Errors never carry ERP text.** `respondErpError` (`lib/payments/publicErpError.ts`) maps any failure through `classifyErpError` and answers `{ error: { message: '<code>' } }`. `lib/payments/errorCopy.ts` holds the code → locale-key vocabulary the frontend renders. Deliberate consequence for `verify`: an unrecognised `status` is **passed through**, not rejected — answering 5xx would be read by the poller as a transient failure and settle optimistically, turning an unknown state into a success. A non-string `status` or `success` is rejected as malformed.
- **Server-authoritative orders (PG-06 + P4.24, 2026-09-14)** — `POST /api/public/erp/payments` no longer proxies the browser's terms. `amount` and `orderReference` in the request body are still ACCEPTED and still shape-validated, but they are **never read**: the price and the reference come from the server, and the ERP request is built field by field (never spread from the request) so a future schema field cannot silently become an ERP input. Four invariants to preserve:
  - **A request must carry `packageId` or `intent`.** With neither, the amount cannot be derived, and the route answers `400 invalid-request` rather than charging a guess. `packageId` is priced against the ERP catalogue (`lib/payments/payablePackage.ts`); `intent` is a signed token from the new `POST /api/public/erp/orders` (`lib/payments/orderIntent.ts`).
  - **A payable package needs a finite, strictly positive `priceMonthly`** and must not be explicitly `isActive: false`. A package with NO price is trial-only — the funnel renders no payment step for it, so a payment request for one is refused, not defaulted. A negative price is dropped by `erpPackageSchema` at the boundary, so its id resolves to `package-not-found`; both refuse the charge.
  - **The reference is minted server-side** — `ord_` + 24 CSPRNG bytes, base64url (192 bits), inside the ERP contract's `^[a-zA-Z0-9_-]{1,64}$`. The component no longer invents `pay-<packageId8>-<Date.now()>`, which was guessable and collided across concurrent payers. Because the server also BUILDS the callback URL, a `packageId`-only client never needs to know the reference at all; the intent carries it for clients that want it up front.
  - **The intent is HMAC-SHA256 signed and can only be carried, never edited.** Payload is `{v, ref, amount, cur, pkg, exp}` — no customer data, since a signature protects integrity, not confidentiality. The key is `sha256('smart-platform.order-intent.v1:' + ERP_TOKEN_ENCRYPTION_KEY)` — domain-separated, so the at-rest ERP token key is not reused raw and `NEXTAUTH_SECRET` stays out of it (see `lib/crypto/erpToken.ts` for the same governance). Missing key throws in production; dev falls back with a warning. TTL 30 min, and expiry is checked AFTER the signature so an unsigned token cannot make the caller do work.
  - **Both directions of the redirect are allow-listed server-side (P4.24)** in `lib/payments/allowlist.ts`. An off-allowlist `callbackUrl` is REJECTED (400), not silently rewritten. The built callback always takes its origin from `APP_URL` and its `order` from the server reference; only a same-origin `/payment/success` (optionally locale-prefixed) path is taken from the client, so the active locale survives the gateway round trip but the host never comes from the caller. A returned `paymentUrl` that is present but off-allowlist is answered `502 erp-malformed-response` — the component's own check runs in the customer's browser and is not a trust boundary. The gateway list must stay identical to `PAYMENT_GATEWAY_HOSTS` in `components/erp/PaymentActivation.tsx` AND the CSP gateway families in `middleware.ts`; `__tests__/lib/payments/allowlist.spec.ts` reads both files and fails if they diverge.
  - **Deploy coupling:** a client that sends neither `packageId` nor `intent` now gets a 400, so the funnel's payment step requires the client half (adding `packageId` to the POST body is a one-line change in `components/erp/PaymentActivation.tsx`).
- **ERP handoff is POST-only (PR #59)** — `lib/erp/handoff.ts` resolves the target via `getErpLoginTargetUrl`, validates it with `isAllowedRedirectUrl`, and `submitErpPostHandoff` submits a hidden form. The ERP login token must never appear in a URL (no `primaryHref` GET link); an off-allowlist target hides the CTA instead.
- **Landing trust strip reads the ERP method catalogue (P2.15 + PG-22)** — `components/landing/TrustStrip.tsx` renders its gateway marks from the live `GET /api/public/erp/methods` catalogue (the second consumer after `components/erp/PaymentActivation.tsx`) instead of a hardcoded array, so the marketing strip cannot advertise a gateway the payment step would not offer. The decision logic lives in `lib/paymentBrands.ts` and is deliberately two-sided: a catalogue that yields **at least one well-formed entry is authoritative** — only entries with `available === true` render, and if _none_ is available the block is omitted entirely (we know the answer, so we do not claim anything); a catalogue that is **unreadable** — request failed, non-array body, empty array, or every row malformed — renders the owner-approved `FALLBACK_PAYMENT_BRANDS` set (we learned nothing, so the strip keeps its shape). `available` is read fail-closed: only the literal `true` proves availability, so an ERP contract change can withhold a mark but never invent one. `Samsung Pay` is deliberately absent from both paths (P2.10 closed; PG-45 tracks the claim).
- **Order receipt (PG-23)** — `components/payment/PaymentReceipt.tsx` is the order summary shown under the result panel on `/payment/success` (both `success` and `pending`) and on `/payment/failed` (reference only, no tax block). Its fields have exactly two sources, and it renders **no placeholder** for anything it could not resolve: the **order reference** comes from the callback URL `?order=` (the only field the URL carries), and the **package name + monthly price** come from the `packageId` the funnel recorded in the payment-in-flight marker (`components/payment/paymentInFlight.ts`, matched on the reference _before_ the marker is cleared) resolved against `GET /api/public/erp/packages`. The merchant tax identity reuses the TRN `310428442600003` phrasing from `/terms`. The `verify` response carries neither a package nor an amount, so an unresolved receipt degrades to the reference alone rather than showing a dash. `/payment/failed` now also links back to `/pricing`, which its copy had been promising without a link.
- **Product-level decision** — smart-platform context decision: _swap Stripe for Moyasar/Tabby/Tamara_. The ERP already wires Moyasar plus Tabby/Tamara mocks; productionize by flipping mock→real providers and auditing committed keys (secrets-hygiene risk).
