# Payments across the product

Purpose: a map of how payments work across the three repos (WebAPI providers + standalone integrations + SPA-side payment UI). Not an implementation doc — see the code and `SmartAndPro.ERP.Inventory/docs/payment-system.md` for details.

## Key points

- **Method → provider (WebAPI `PaymentService`)** — current mapping: `card`/`mada`/`apple_pay` → **MoyasarProvider** (`PaymentService.cs`), `tabby` → **TabbyProvider** (mock), `tamara` → **TamaraProvider** (mock), `stc_pay` → **HyperPayProvider** (mock). **PaymobProvider** remains an available real provider (3-step token→order→payment-key) but is NOT the current selection for those methods. Map persisted in the `Payments` table; endpoint `POST /api/payments`, methods `GET /api/payments/methods?country=SA`.
- **Paymob (real)** — SPA drives the flow: `services/paymob` (`environment.paymob`: currency `EGP`, `integrationId` 5410149, `accept.paymob.com`) with `payment-callback.component` for the SPA-side return; WebAPI `PaymobProvider` handles the server side (`PaymobService` in Application layer).
- **Moyasar (current card/mada/apple_pay provider)** — `Providers/MoyasarProvider.cs`, registered in `Program.cs`/`PaymentService`, configured under `PaymentProviders:Moyasar` (a live-looking `sk_test_...` key is committed). Not yet covered by `docs/payment-system.md` — treat the map above as current truth.
- **Standalone commerce/health integrations (not `PaymentService`)** — Salla and Zid (OAuth e-commerce, webhooks redirect to `erp.smartapro.com`), Wasafaty + CCHI (both NPHIES FHIR R4), ChannelManager (background sync service). Config under Salla/Zid/Wasafaty/CCHI/ChannelManager in `appsettings.json`.
- **Kit payment-result flow (`pages/payment/success.tsx`)** — after a gateway redirect the page polls the BFF `GET /api/public/erp/verify?reference=…` up to 15×2s (`attempts`/`interval` query knobs are localhost-only for e2e). Terminal states: `Failed` (or `success:false`) → `/payment/failed`; `Paid` → confirmed success copy + POST ERP handoff; explicit `Pending` at poll end → pending panel with **no** ERP CTA (the webhook activates the subscription); no `status` in the response (absent or blank) → **optimistic settle** kept for pre-P2.14 ERPs, which becomes unreachable once the ERP always returns `status`. A `status` that is present but **unrecognised** (e.g. `Succeeded`, a mistyped enum) polls to the pending panel and never claims success or hands over the ERP token. Non-2xx `verify` responses are split explicitly: a **4xx other than 429** is a permanent client-side rejection (unknown/oversized reference) and is a hard error that ends on the error panel, while a **429 or any 5xx** is a transient infrastructure failure whose body is never parsed — it falls through to the normal poll path, so an ERP/BFF outage during the poll window still settles optimistically rather than dead-ending a customer who already paid.
- **Public funnel BFF response contract (PG-20/PG-30/PG-52/PG-54, 2026-09-14)** — the four anon routes under `pages/api/public/erp/` (`methods`, `packages`, `verify`, `payments`) validate the ERP body and answer failures with a **stable code**, never upstream text. Three invariants to preserve when editing them:
  - **Contracts live in `lib/zod/erp.ts`** (`erpPaymentMethodSchema`, `erpPackageSchema`, `erpVerifyResponseSchema`, `readErpList`) and are applied in `lib/erp.ts` (`fetchAvailableMethods`, `fetchPackages`, `fetchVerifyResult`), not in the routes — so `/pricing`, which calls `getPackages()` straight from `getServerSideProps`, is covered by the same guard. Envelope strictness is all-or-nothing (a non-array list or a non-object verify body throws `ErpApiError('ERP_MALFORMED_RESPONSE', 502)`); **entry** strictness is per-item (a bad entry is dropped, one bad row never takes the catalogue down).
  - **Fail-closed on availability.** `erp.getMethods()` returns only entries the ERP marked `available: true`; an entry with a missing or non-boolean `available` is discarded rather than offered. A malformed `priceMonthly` **rejects its package** (absence of a price already renders as "Free" in `pages/pricing.tsx`, so a corrupt price could only become a false claim), while `description`/`priceYearly`/`trialDays`/`isActive` are merely dropped.
  - **Errors never carry ERP text.** `respondErpError` (`lib/payments/publicErpError.ts`) maps any failure through `classifyErpError` and answers `{ error: { message: '<code>' } }`. `lib/payments/errorCopy.ts` holds the code → locale-key vocabulary the frontend renders. Deliberate consequence for `verify`: an unrecognised `status` is **passed through**, not rejected — answering 5xx would be read by the poller as a transient failure and settle optimistically, turning an unknown state into a success. A non-string `status` or `success` is rejected as malformed.
- **ERP handoff is POST-only (PR #59)** — `lib/erp/handoff.ts` resolves the target via `getErpLoginTargetUrl`, validates it with `isAllowedRedirectUrl`, and `submitErpPostHandoff` submits a hidden form. The ERP login token must never appear in a URL (no `primaryHref` GET link); an off-allowlist target hides the CTA instead.
- **Product-level decision** — smart-platform context decision: _swap Stripe for Moyasar/Tabby/Tamara_. The ERP already wires Moyasar plus Tabby/Tamara mocks; productionize by flipping mock→real providers and auditing committed keys (secrets-hygiene risk).
