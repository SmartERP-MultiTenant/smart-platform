# Demo seed — local dataset + server runbook

Plain-SQL demo fixtures for the smart-platform database, plus the operator runbook
for applying them (and for granting the platform-admin role) on the server.

Everything here is **psql (Postgres)** except `erp-paid-packages.sql`, which is
**T-SQL** against the ERP database. That distinction is called out again where it
matters.

---

## 1. Who this is for

The owner wants to exercise every flow in the product. The stock `prisma/seed.ts`
cannot do that: it creates random faker rows with no ERP link, no billing shape, no
account-state coverage, and — critically — it is **not idempotent** (re-running it
creates a second set of random users and teams).

This dataset is deterministic, idempotent, exactly reversible, and namespaced so it
can never touch real data.

|                    | `prisma/seed.ts`           | this dataset                                             |
| ------------------ | -------------------------- | -------------------------------------------------------- |
| Data               | random (faker)             | deterministic, reviewable                                |
| Re-runnable        | no — duplicates every time | yes — 0 new rows, 0 errors                               |
| Removable          | manually                   | `00-teardown.sql`, exact                                 |
| Runs on the server | **no** (see §7)            | yes (`psql`)                                             |
| Covers             | users/teams/invitations    | + account states, billing, API keys, audit log, ERP link |

## 2. Files

| File                            | Dialect                | Writes                                                                       |
| ------------------------------- | ---------------------- | ---------------------------------------------------------------------------- |
| `all.sql`                       | Postgres               | conductor — applies 01→06 in one transaction                                 |
| `01-users.sql`                  | Postgres               | 12 users (every account state the schema supports)                           |
| `02-teams-memberships.sql`      | Postgres               | 3 teams + 8 memberships + renewal-reminder state                             |
| `03-invitations.sql`            | Postgres               | 4 invitations (pending + expired)                                            |
| `04-billing.sql`                | Postgres               | 2 services, 3 prices, 2 subscriptions                                        |
| `05-apikeys-auditlog.sql`       | Postgres               | 3 API keys, 3 admin-audit rows                                               |
| `06-erp-link.sql`               | Postgres               | ERP link on the flagship team (**local ERP facts**)                          |
| `local/all-local.sql`           | Postgres               | **local entry point** — sets the committed dev hash, then includes `all.sql` |
| `server/apply-server.sql`       | Postgres               | **non-local entry point** — same dataset, requires a caller-supplied hash    |
| `server/06-erp-link.server.sql` | Postgres               | ERP link with **production** tenant GUID + API URL                           |
| `erp-paid-packages.sql`         | **T-SQL / SQL Server** | 3 paid packages + package modules + the demo tenant's subscription modules   |
| `erp-teardown.sql`              | **T-SQL / SQL Server** | reverses `erp-paid-packages.sql` exactly                                     |
| `00-teardown.sql`               | Postgres               | removes all of the above, exactly                                            |

### Which entry point am I allowed to use?

| Target        | Entry point               | Password hash                               |
| ------------- | ------------------------- | ------------------------------------------- |
| local dev box | `local/all-local.sql`     | committed dev hash, supplied by the wrapper |
| anything else | `server/apply-server.sql` | **must** be passed by the operator (`-v`)   |

`local/all-local.sql` is the only file permitted to carry a usable hash, and that hash
is public by construction because it is committed. **It must never be pointed at a
non-local database.** The server path cannot run without an explicit hash — see §5.

### The id namespace

Every platform row carries an explicit id in the reserved block
`00000000-de30-4000-8000-*`, and billing rows use the text prefixes
`service_demo_` / `price_demo_` / `sub_demo_`. **Ids are explicit because they must
be**: the live Postgres DDL gives these columns _no_ database default — Prisma's
`@default(uuid())` is generated by the Prisma client, not by the database — so an
`INSERT` that omits an id fails outright. Teardown matches on that namespace.

## 3. Prerequisites

```text
postgres container `saas-postgres` on host port 5433   (db saas, user postgres)
DATABASE_URL=postgresql://postgres:postgres@localhost:5433/saas
schema already applied  →  the tables in `prisma/migrations/` (authoritative)
```

The schema is assumed to be present already. Do **not** run `npx prisma db push` to
"make sure": this repo treats `prisma/migrations/` as authoritative, and prod schema
changes go through `prisma migrate deploy` (see `docs/CI-CD.md`). `db push` is a
schema-driven sync that bypasses migration history — if the local tables are missing,
apply the migrations.

## 4. Applying it

```bash
cd /mnt/Projects/Kayan/website/smart-platform
export DATABASE_URL=postgresql://postgres:postgres@localhost:5433/saas

# all of it, atomically — the local entry point supplies the dev hash
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -f prisma/demo/local/all-local.sql

# or a single file, wrapped in a transaction by psql itself
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 --single-transaction -f prisma/demo/04-billing.sql
```

Every file is idempotent: run the wrapper twice and the second run creates **zero**
rows and reports no error.

> **Do not add `--single-transaction` to `all.sql`.** The conductor already opens
> `BEGIN`/`COMMIT`; nesting a second `BEGIN` inside psql's own single transaction
> makes the inner `COMMIT` end the transaction early, so later statements would run
> outside the atomic block. Use the flag for _individual_ files, as above.

### Tearing it down

```bash
psql "$DATABASE_URL" -v ON_ERROR_STOP=1 --single-transaction -f prisma/demo/00-teardown.sql
```

`00-teardown.sql` deletes children before parents and matches **only** the reserved
id namespace and the demo natural keys — and every natural key is an **exact** match,
never a prefix pattern:

| Signal            | Predicate                                                          |
| ----------------- | ------------------------------------------------------------------ |
| Team slugs        | `IN ('demo-alpha','demo-beta','demo-gamma')`                       |
| Emails            | the twelve `demo-*@demo.smartapro.com` addresses, listed literally |
| Invitation tokens | `demo-invite-token-%`                                              |
| Billing ids       | `service_demo_` / `price_demo_` / `sub_demo_` prefixes             |

Exactness is load-bearing, not tidiness. Team slugs are slugified from a **user-typed
team name**, so a real customer who names their workspace "Demo Store" gets slug
`demo-store` — a `slug LIKE 'demo-%'` predicate deletes their team _and cascades_ its
memberships, invitations and API keys. (Earlier revisions used `demo-%` here; the fix
is covered by a regression proof in which a sentinel `demo-store` team, its membership
and its user survived teardown while all 40 demo rows were removed.) `smaartx7@gmail.com`,
real team slugs, and Stripe-synced `Service`/`Price` rows are therefore unreachable by
construction. It prints a per-table row-count report afterwards so the operator can
compare against the pre-seed counts.

### Verifying

```bash
psql "$DATABASE_URL" -c '
SELECT '"'"'users'"'"' t, count(*) FROM "User" WHERE email LIKE '"'"'demo-%@demo.smartapro.com'"'"'
UNION ALL SELECT '"'"'teams'"'"', count(*) FROM "Team" WHERE slug LIKE '"'"'demo-%'"'"'
UNION ALL SELECT '"'"'members'"'"', count(*) FROM "TeamMember"
UNION ALL SELECT '"'"'invitations'"'"', count(*) FROM "Invitation"
UNION ALL SELECT '"'"'api keys'"'"', count(*) FROM "ApiKey"
UNION ALL SELECT '"'"'audit rows'"'"', count(*) FROM "AdminAuditLog";
'
```

Expected: 12 users, 3 teams, 8 members, 4 invitations, 3 API keys, 3 audit rows.

**(local only)** — the member / invitation / API-key / audit-row counts are unfiltered,
so they hold on a database that contains nothing but this dataset. On the server the
same query is the **pre-seed baseline** from §7.2 and its numbers will be higher.

## 5. Demo credentials

All demo users in an environment share **one** password. The bcrypt hash (bcryptjs, 12
rounds — the cost `lib/auth.ts` uses, so `compareSync` accepts it verbatim) is **not**
stored in `01-users.sql`: it is a required psql variable. Two hash sources exist, and
exactly one of them is committed:

| Environment | Who supplies the hash             | Committed?                               |
| ----------- | --------------------------------- | ---------------------------------------- |
| local       | `local/all-local.sql`             | yes — public by construction, local only |
| server      | the operator, via `-v` on the CLI | **never**                                |

`01-users.sql` fails closed when the variable is missing or empty (exit 3, message
naming the variable), so the earlier design — embed one committed hash, then remember
to rotate it afterwards — is gone. A step that can be forgotten is not a control; the
requirement is now structural. Probed behaviour and the two mechanisms used are
documented at the top of `01-users.sql`.

| Email                                    | State                                      | Teams                                   |
| ---------------------------------------- | ------------------------------------------ | --------------------------------------- |
| `demo-platform-admin@demo.smartapro.com` | **PLATFORM_ADMIN** — full `/admin` console | none (by design)                        |
| `demo-owner@demo.smartapro.com`          | verified                                   | `demo-alpha` **OWNER**                  |
| `demo-admin@demo.smartapro.com`          | verified                                   | `demo-alpha` ADMIN                      |
| `demo-member@demo.smartapro.com`         | verified                                   | `demo-alpha` + `demo-beta` MEMBER       |
| `demo-member2@demo.smartapro.com`        | verified                                   | `demo-alpha` MEMBER                     |
| `demo-owner2@demo.smartapro.com`         | verified                                   | `demo-beta` OWNER                       |
| `demo-erp-owner@demo.smartapro.com`      | verified                                   | `demo-gamma` OWNER                      |
| `demo-invitee@demo.smartapro.com`        | verified                                   | none — target of the pending invitation |
| `demo-unverified@demo.smartapro.com`     | `emailVerified IS NULL`                    | `demo-gamma` MEMBER                     |
| `demo-locked@demo.smartapro.com`         | locked (`lockedAt` + 5 failed attempts)    | none                                    |
| `demo-disabled@demo.smartapro.com`       | `disabledAt` set                           | none                                    |
| `demo-noteam@demo.smartapro.com`         | verified, no team                          | none                                    |

**No plaintext password is in this repository**, and the only hash it contains is the
local dev one in `local/all-local.sql`. Both plaintexts are handed over out-of-band by
whoever runs the seed. To change one, generate a new bcryptjs hash and either replace
the literal in `local/all-local.sql` (local) or pass it to the server conductor.

The same applies to the three API-key **raw** values whose sha256 digests are in
`05-apikeys-auditlog.sql` — recorded out-of-band for completeness. Note they are not
needed for any flow: **no code path in this repo verifies a presented API key**
(`grep -rn hashedKey` finds only the writer in `models/apiKey.ts`), so the API-key
surface is settings-UI only.

### The three demo teams

| Slug         | Shows                                                                                                                  |
| ------------ | ---------------------------------------------------------------------------------------------------------------------- |
| `demo-alpha` | **ERP-linked** flagship: custom `domain`, active billing customer, API keys, pending + expired invitations, audit rows |
| `demo-beta`  | **cancelled** subscription, a reminder already sent (`lastReminderStage='T-7'`), unlinked from the ERP                 |
| `demo-gamma` | **unlinked** (no ERP, no billing), non-default `defaultRole`, holds the unverified member                              |

## 6. ERP side (`erp-paid-packages.sql`) — T-SQL, not Postgres

The ERP self-seeds on boot: 14 SystemModules, 1 `Starter` package priced **0.00**, and
the `demo` tenant. A zero-priced package is trial-only — `lib/payments/payablePackage.ts`
requires a finite, strictly positive `priceMonthly`, so the funnel renders no payment
step and `POST /api/public/erp/payments` answers `400 invalid-package`. This file adds
real paid packages so the pricing → payment path is reachable.

```bash
docker exec -i sqlserver /opt/mssql-tools18/bin/sqlcmd \
  -S localhost -U sa -P 'YourStrong@Passw0rd' -C -d Erp -b \
  < /mnt/Projects/Kayan/website/smart-platform/prisma/demo/erp-paid-packages.sql
```

It is idempotent (deterministic package GUIDs, plus a name-based guard in case the
packages were created through the ERP admin UI first). It also populates the demo
tenant's `SubscriptionModules`, which the ERP derives the JWT's `ActiveModules` claim
from — without those rows the ERP client app has no modules enabled.

**Rollback is `erp-teardown.sql`**, which restores the pre-seed ERP state exactly
(`Packages` 4 → 1, `PackageModules` 46 → 14, `SubscriptionModules` 14 → 0):

```bash
docker exec -i sqlserver /opt/mssql-tools18/bin/sqlcmd \
  -S localhost -U sa -P 'YourStrong@Passw0rd' -C -d Erp -b \
  < /mnt/Projects/Kayan/website/smart-platform/prisma/demo/erp-teardown.sql
```

What it reverses matters: the seed did **not** move the demo subscription onto a new
package — it left it on `Starter` and copied _that_ package's modules into
`SubscriptionModules`. The rollback therefore mirrors the seeder's own join condition
instead of filtering on the three demo package GUIDs (which are not what those rows
came from). Packages and their modules are deleted by deterministic GUID only, so a
pre-existing package the seed linked to via its name-fallback path is never deleted.

**Nothing here is applied to the server automatically.** The server's ERP database is
a different host and a different database engine; treat this file as local-only unless
you deliberately decide otherwise.

## 7. Server runbook

### 7.1 Why `psql` and not the repo's own scripts

`npm run seed:platform-admin` **cannot run on the server.** The runtime image
(`Dockerfile`, runner stage) copies only `package*.json`, `node_modules`, `.next`,
`public`, `prisma`, `next.config.js`, `next-i18next.config.js`, `locales` and the
entrypoint — there is **no `scripts/` directory and no `tsconfig.json`** in the
container. `npx prisma db seed` is also unreliable there (ts-node type-checks, and
without a tsconfig it cannot resolve `require`). `psql` is the supported mechanism, and
it matches this repo's existing operator runbook for the admin role
(`docs/platform-admin-bootstrap.md`).

### 7.2 Backup first — non-negotiable

```bash
ssh root@204.44.87.208
cd /var/www/multitenant-smart-and-pro

# the platform container holds the runtime DB URL (Compose hostname, NOT localhost:5433)
DBURL=$(docker exec erp-platform printenv DATABASE_URL)
DBUSER=$(printf '%s' "$DBURL" | sed -E 's#postgresql://([^:]+):.*#\1#')
DBNAME=$(printf '%s' "$DBURL" | sed -E 's#.*/([^/?]+)(\?.*)?$#\1#')
PGC=$(docker compose ps -q postgres)

echo "target: user=$DBUSER db=$DBNAME"
docker exec "$PGC" pg_dump -U "$DBUSER" -d "$DBNAME" -Fc -f /tmp/pre-demo.dump
docker cp "$PGC":/tmp/pre-demo.dump ./pre-demo-$(date +%Y%m%d%H%M%S).dump
ls -lh pre-demo-*.dump
```

Record the pre-seed row counts too, so the teardown report has something to compare
against (`psql -c` with the query in §4, run before applying).

### 7.3 Copy and apply

Copy the **whole tree**, not just the top-level files — the conductors use `\ir`, and
that resolves against the filesystem of whatever process runs `psql` (inside the
container, in this runbook), so the numbered files have to be present there too.

```bash
# from the workstation
scp -r smart-platform/prisma/demo root@204.44.87.208:/tmp/demo-seed
```

Generate a **server-only** hash on the workstation — never reuse the committed dev one.
`read -s` keeps the plaintext out of the shell history and out of `ps`:

```bash
export PATH="$PATH"   # bcryptjs comes from the repo's node_modules
read -rsp 'demo password: ' DEMO_PW; echo
DEMO_HASH=$(node -e "process.stdout.write(require('bcryptjs').hashSync(process.argv[1],12))" "$DEMO_PW") || exit 1
unset DEMO_PW
printf '%s\n' "$DEMO_HASH"   # sanity: starts with $2b$12$ and is 60 chars
```

```bash
# on the server
cd /var/www/multitenant-smart-and-pro
DBURL=$(docker exec erp-platform printenv DATABASE_URL)
DBUSER=$(printf '%s' "$DBURL" | sed -E 's#postgresql://([^:]+):.*#\1#')
DBNAME=$(printf '%s' "$DBURL" | sed -E 's#.*/([^/?]+)(\?.*)?$#\1#')
PGC=$(docker compose ps -q postgres)

# the conductor's `\ir` resolves INSIDE the container, so the tree goes there
docker cp /tmp/demo-seed "$PGC":/tmp/demo-seed

docker exec -i "$PGC" psql -U "$DBUSER" -d "$DBNAME" -v ON_ERROR_STOP=1 \
  -v demo_password_hash="$DEMO_HASH" -f /tmp/demo-seed/server/apply-server.sql
```

Notes on this shape:

- **Do not include `--single-transaction`.** `apply-server.sql` opens its own
  `BEGIN`/`COMMIT`; nesting a second one lets the inner `COMMIT` end the transaction
  early. Same rule as `../all.sql`.
- **`server/apply-server.sql`, never `local/all-local.sql`.** The server conductor
  applies `06-erp-link.server.sql` (production tenant GUID + `server-mt` API URL); the
  local one would write a `localhost` API URL that is unreachable from inside the
  container. It also refuses to carry a hash.
- **`erp-paid-packages.sql` is not part of this run.** It is T-SQL against the ERP
  database, and the server's ERP already has paid packages (Basic 99 / Professional
  199 / Enterprise 349), so `/pricing` works there without it.
- **What is exposed by `-v`.** Only the bcrypt hash reaches `argv`, never the
  plaintext, and only for the lifetime of that process. The hash is salted, so it is
  not itself a login credential — but the plaintext must still never be passed this
  way, which is why it is read with `read -s` and only ever piped into `node`.
- **If the hash is forgotten, the apply aborts.** `01-users.sql`'s guard raises
  (`exit 3`, message naming `demo_password_hash`) before the first `INSERT`; nothing is
  written and the transaction rolls back.

### 7.4 Verify

```bash
docker exec "$PGC" psql -U "$DBUSER" -d "$DBNAME" -c '
SELECT count(*) FILTER (WHERE email LIKE '"'"'demo-%@demo.smartapro.com'"'"') AS demo_users,
       count(*) FILTER (WHERE "platformRole" = '"'"'PLATFORM_ADMIN'"'"') AS platform_admins
FROM "User";'
```

Then log in as `demo-platform-admin@demo.smartapro.com` and confirm `/admin` returns
200 while a non-admin account returns 403.

### 7.5 Rollback

Preferred — restore the dump (exact, and it also undoes anything else that changed):

```bash
docker exec -i "$PGC" pg_restore -U "$DBUSER" -d "$DBNAME" --clean --if-exists < pre-demo-<ts>.dump
```

Narrower — remove only the demo rows:

```bash
docker exec -i "$PGC" psql -U "$DBUSER" -d "$DBNAME" \
  -v ON_ERROR_STOP=1 --single-transaction -f - < /tmp/demo-seed/00-teardown.sql
```

> ### ⚠️ The full dataset on the server is a deliberate, consequential choice
>
> The operator decided to apply the **full** dataset in production, not a stripped
> subset. These are the surfaces that actually show it — verify rollback on these,
> **not** on `/admin/revenue`:
>
> | Surface                        | What appears                                                        |
> | ------------------------------ | ------------------------------------------------------------------- |
> | `/admin/users`                 | the 12 demo users, presented as real customers                      |
> | `/admin` overview tenant table | the 3 demo teams (`lib/adminDashboard.ts` → `prisma.team.findMany`) |
> | `/admin/audit-logs`            | the 3 demo audit rows                                               |
> | team dashboard tiles           | `Service`/`Price` counts (`models/dashboard.ts`)                    |
>
> **`/admin/revenue` is NOT affected.** That route reads only the ERP M2M aggregate
> (`pages/api/admin/revenue.ts` → `erp.listSubscriptionsM2M`) and makes **zero** prisma
> calls, so the seeded `Subscription`/`Price` rows never reach it. An earlier revision
> of this file claimed they did; that was wrong.
>
> Postgres rollback is `00-teardown.sql` (exact, per §4) and the ERP-side data added by
> §6 is reversed by `erp-teardown.sql`. Together they restore the pre-seed state. If
> the full dataset is not wanted, apply only `01-users.sql` + `06-erp-link.sql` + the
> admin grant in §8 and skip `02`–`05`.

## 8. Granting the owner's account (create-if-missing)

The operator decided `smaartx7@gmail.com` becomes a **platform admin**, creating the
account if it does not exist. `docs/demo-seed-and-admin-grant.md` §5 has the full
block; the shape is:

1. look the user up by `lower(email)`;
2. if absent, `INSERT` with an explicit id, a `name` (NOT NULL — the stock
   bootstrap script would have failed here), `emailVerified = now()`, and a bcrypt
   hash;
3. `UPDATE` `platformRole = 'PLATFORM_ADMIN'` guarded by `GET DIAGNOSTICS`, raising
   unless **exactly one** row was affected.

This path also **bypasses the free-mail signup gate**: `lib/email/utils.ts` blocks
free-mail domains (including `gmail.com`) when `DISABLE_NON_BUSINESS_EMAIL_SIGNUP=true`,
in `pages/api/users.ts`, `pages/api/auth/join.ts` and `lib/nextAuth.ts`. If the server
has that flag on, a Gmail account can neither register nor sign in — so check it
before assuming self-service registration is an option.

## 10. Notes for maintainers

- **sqlfluff reports `LXR`/`PRS` on these files.** It flags `\set` and `\echo` because
  they are psql _client_ meta-commands, not SQL, and it cannot lex them. The same
  applies to the T-SQL file when linted with a Postgres dialect. These are tool
  limitations — `\set ON_ERROR_STOP on` is load-bearing (it protects a file run
  without the `-v` flag), so do not delete it to silence the warning.
- **The server image ships no `scripts/`** — any future need to run repo tooling on
  the server requires fixing `Dockerfile`, not working around it.
- **The demo password hash is a required input, not a literal.** If you are tempted to
  reinstate a default in `01-users.sql` to make some call site simpler, read the guard's
  header first: the failure mode it removes is a committed, publicly readable password
  being re-installed on a live system by a routine re-apply. `local/all-local.sql` is
  the sanctioned default, and it is local-only.
- **The ERP package endpoint must be live** for `/pricing`, the funnel, and the admin
  console's ERP reads. If the ERP backend on the server is stale, those pages fail
  regardless of seeding. (It was verified live on 2026-09-24: the VPS clone sits on
  `deploy` @ `2cb867b3` and `/api/platform/billing/*` answers 401 — route present,
  key required — rather than 404.)
